## چرا حسابفا و نه سپیدار یا هلو؟

من مستندات عمومی هر سه را بررسی کردم. **حسابفا** انتخاب درست است:

| معیار | سپیدار / هلو | حسابفا |
|---|---|---|
| نوع محصول | نرم‌افزار دسکتاپ (Windows نصب می‌شود) | **وب‌اپلیکیشن** — دقیقاً مثل پنل فعلی شما |
| ساختار منو | پراکنده و بسته به نسخه | **منوی موضوعی روشن**: اشخاص ← کالا ← بانکداری ← فروش ← خرید ← انبارداری ← حسابداری ← گزارشها ← تنظیمات |
| بستن سال مالی | نامشخص در منو | **صریح**: یک آیتم مستقل به نام «بستن سال مالی» |
| تراز افتتاحیه | نامشخص | **صریح**: آیتم مستقل |
| جدول حساب‌ها | نامشخص | **صریح**: آیتم مستقل |
| تنظیمات چاپ | نامشخص | **صریح**: آیتم مستقل |
| فروش اقساطی/ اعتباری | نامشخص | **صریح**: «قرارداد فروش اقساطی» و «فروش اقساطی» |
| بانکداری | عمومی | **جدا**: بانکها / صندوقها / تنخواه‌گردان / انتقال / چک دریافتی / چک پرداختی |
| گزارش‌ها | عمومی | **تفکیک‌شده**: مالی / اشخاص / کالا و خدمات / خرید و فروش / بانکداری |

**نتیجه:** حسابفا وب‌اپ است، منویش موضوعی و دقیقاً همان ساختاری است که شما خواستید (انبار زیرمجموعهٔ حسابداری، نه بخش جدا). سپیدار و هلو دسکتاپ‌اند و منویشان برای این پروژه الگوی خوبی نیست.

## پاسخ به سؤال ۳: «خودکار چطور میشه، دستی چطور میشه؟»

حقوق دستی یعنی هر بار باید خودتان بنویسید. حقوق خودکار یعنی:

1. در تنظیمات، برای هر کارمند **حقوق ماهانه** و **ساعات کاری** را یک‌بار وارد می‌کنید.
2. آخر ماه یک دکمه می‌زنید: **«محاسبه حقوق این ماه»**.
3. سیستم خودش برای هر کارمند سند می‌زند:

```
بدهکار  6030  هزینهٔ حقوق و دستمزد      ۵۰٬۰۰۰٬۰۰۰
   بستانکار  2100  حساب‌های پرداختنی کارکنان   ۵۰٬۰۰۰٬۰۰۰
```

مزیت: دیگر لازم نیست دستی بنویسید، ولی **کنترل کامل دست شماست** (می‌توانید قبل از ثبت، پیش‌نویس را ببینید و اصلاح کنید).

پیاده‌سازی در **فاز ۲** انجام می‌شود.

## یافتهٔ بحرانی: سیستم مالی ناسازگار است

تحقیق دقیق یک ایراد بسیار خطرناک پیدا کرد:

**سال مالی هیچ‌وقت بسته نمی‌شود و هیچ راهی برای ساختنش وجود ندارد.** فقط در `seed.ts` ساخته می‌شود. هر بار که تست‌ها اجرا می‌شوند یک سال `OPEN` جدید می‌سازند — الان **۵ سال مالی باز** هم‌زمان در دیتابیس وجود دارد.

و چون `journal.service.ts:168` از `findFirst({ state: "OPEN" })` **بدون orderBy** استفاده می‌کند، اسناد به‌صورت تصادفی بین این ۵ سال پخش می‌شوند.

**اگر سایت روی هاست برود و سال مالی باز نباشد:**

| مسیر | چه اتفاقی می‌افتد |
|---|---|
| صندوق، خزانه، چک، خرید | **کل عملیات پسگرفته می‌شود** — مشتری نمی‌تواند بخرد |
| فروش آنلاین | **پول در بانک می‌نشیند، مشتری پیامک می‌گیرد، موجودی کم می‌شود، ولی هیچ سندی ثبت نمی‌شود** |

بدترین حالت ممکن: فروش انجام می‌شود و دفاتر بی‌خبر می‌مانند.

**به همین دلیل فاز صفر با سیستم سال مالی شروع می‌شود، نه با ظاهر کردن رابط کاربری.**

#### چرا آداپتورهای درگاه‌ها مسدود است

پژوهش وب انجام شد ولی **مستندات عمومی API تسویهٔ اسنپ‌پی/ترب‌پی/دیجی‌پی در دسترس نبود** — نتایج مربوط به شرکت‌های دیگر بود (SnapPay آفریقای جنوبی، Tribe Pay، TerraPay). نوشتن آداپتور از روی حدس، کدی می‌سازد که **شبیه واقعیت است ولی در تولید شکست می‌خورد**.

برای ادامه یکی از این‌ها لازم است:
۱. لینک مستندات API درگاه موردنظر
۲. یا credential حساب تست (sandbox) + یک پرداخت آزمایشی واقعی

6. **سند خودکار هم قابل اصلاح است** — با همان مکانیزم برگشت به پیش‌نویس که الان ساخته شد

## ریسک‌ها

| ریسک | راه‌حل |
|---|---|
| تغییر کدینگ، اسناد قدیمی را بی‌معنا کند | کدهای فعلی حفظ می‌شوند؛ فقط زیرحساب اضافه می‌گردد |
| پیچیدگی → پروژه از کار بیفتد | بکاپ قبل از هر فاز + فازبندی مستقل |
| منوی جدول گم‌شود | هر آیتم منو صفحهٔ مستقل خودش دارد، ریسکی نیست |
| تست‌های موجود بشکنند | قبل از هر فاز تست کامل ۱۷۶تایی اجرا می‌شود |
