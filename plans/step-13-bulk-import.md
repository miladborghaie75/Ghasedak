## ۲) تعریف «تمام‌شده» (پذیرش نقشه + افزوده)

> پذیرش نقشه: «فایل ۱۰۰سطری نمونه → پیش‌نمایش درست → اعمال → rollback پاک.»

- **پیش‌نمایش:** برای هر ردیف، تصمیم صریح: `CREATE` / `UPDATE` (با فهرست فیلدهای تغییریافته و قبل/بعد) / `SKIP` (با دلیل) / `ERROR` (با ستون و پیام فارسی).
- **اعمال:** همه‌یا‌هیچ در یک تراکنش با `batchId`؛ صفر نوشتن نیمه‌کاره؛ شمارش نهایی = همان عدد پیش‌نمایش.
- **Rollback:** برمی‌گرداند آنچه آن batch ساخته (محصول تازه → آرشیو/حذف منطقی؛ فیلد تغییرکرده → مقدار قبل؛ حرکت انبار → حرکت معکوس) و idempotent است (اجرای دوباره = بی‌اثر).
- **صداقت داده:** هیچ ردیفی بی‌صدا رد نمی‌شود؛ ردیف ناخوانا/تکراری/بدون SKU **گزارش** می‌شود.
- **شاهد:** فایل ۱۰۰سطری واقعی + تست + اسکرین‌شات پیش‌نمایش/نتیجه + Audit.

## ۴) گام‌های اجرا

### ۱۳-۰ — تصمیم‌های باز را قطعی کن (S)
دو پرسش بخش ۵ باید قبل از کد پاسخ بگیرند (پیشنهاد من ثبت شده است). همین گام شامل **بازتولید وضعیت فعلی** با یک فایل نمونهٔ دستی است تا نقاط شکست واقعی (نام تکراری، SKU ناموجود، قیمت فارسی) دیده شود.

### ۱۳-۱ — پارسر CSV خالص + گارد (M)
**فایل تازه:** `apps/api/src/import/csv-parse.ts` (خالص، بدون وابستگی).
- RFC4180: نقل‌قول، کامای داخل نقل‌قول، پایان خط `\n`/`\r\n`، BOM اختیاری اول فایل (همان چیزی که خودمان صادر می‌کنیم).
- نرمال‌سازی ورودی انسانی: ارقام فارسی/عربی → لاتین، جداکنندهٔ هزارگان، `ي`/`ك` عربی → فارسی، فاصلهٔ اضافی.
- سطر/ستون نامعتبر → خطای دقیق (`row`, `column`) نه پیام کلی.
**پذیرش:** تست خالص: فایل با BOM، کاما داخل نقل‌قول، سطر ناقص، رقم فارسی، فایل خالی.
**ریسک:** پارسر دست‌نویس می‌تواند در لبه‌ها اشتباه کند → تست‌های لبه‌ای اجباری؛ اگر جایی پیچیده شد، همان‌جا دربارهٔ وابستگی تصمیم دوباره گرفته می‌شود.

### ۱۳-۲ — مدل دستهٔ ورود + مهاجرت (S/M)
**فایل‌ها:** `schema.prisma` + migration تازه.
```
ImportBatch:  id, kind(PRODUCTS), filename, actorId, status(PREVIEWED|APPLIED|REVERTED|FAILED),
              rowCount, createCount, updateCount, skipCount, errorCount,
              previewHash, appliedAt, revertedAt, createdAt
ImportBatchRow: id, batchId, rowNo, action(CREATE|UPDATE|SKIP|ERROR),
              entityType, entityId, sku, before(Json?), after(Json?), message, appliedAt
```
- `previewHash` = هش محتوای فایل + بازهٔ هدف؛ جلوی «اعمال فایل اشتباه روی پیش‌نمایش قدیمی» را می‌گیرد (idempotency واقعی).
**پذیرش:** مهاجرت روی DB تمرین اعمال، `prisma generate` سبز؛ ایندکس `(batchId, rowNo)` و `(status)`.

### ۱۳-۳ — سرویس پیش‌نمایش (M)
**فایل تازه:** `apps/api/src/import/import.service.ts`.
- ورودی: متن فایل (base64 در بدنه، مثل رسانه) + `kind`.
- خروجی: `{ batchId, previewHash, rows: [...] , counts }` — **هیچ نوشتنی روی محصولات**.
- تطبیق ردیف: SKU موجود → `UPDATE` با diff فیلدها؛ SKU تازه → `CREATE`؛ ردیف تکراری در همان فایل → `ERROR` («SKU تکراری در سطر ۴۲»)؛ دسته/برند ناموجود → تصمیم صریح (بند ۵).
- اعتبارسنجی از همان قواعد موجود: `text-guard`، قیمت غیرمنفی، موجودی صحیح.
- ذخیرهٔ `ImportBatch`+ردیف‌ها با وضعیت `PREVIEWED` (تا Rollback و Audit معنا داشته باشد).
**پذیرش:** فایل ۱۰۰سطری → شمارش‌ها با انتظار دستی یکی باشد؛ DB محصولات **بی‌تغییر** (شاهد: قبل/بعد count).

### ۱۳-۴ — سرویس اعمال (M)
- پیش‌شرط: `previewHash` همان باشد (وگرنه `PREVIEW_STALE` صریح).
- اجرا در **یک تراکنش**: برای هر ردیف `createFull`/`updateFull` + برای موجودی اولیه `InventoryService.moveInTx(kind: OPENING, unitCost)`.
- منطق مشترک با فرمهای ادمین (بدون بازنویسی قواعد محصول/انبار).
- شکست یک ردیف → **همهٔ تراکنش rollback**؛ ردیف مقصر با شماره سطر گزارش می‌شود.
- `AuditLog` برای عمل `import.apply` با `batchId`.
**پذیرش:** اعمال ۱۰۰ ردیف؛ شمارش‌ها = پیش‌نمایش؛ قیمت/موجودی/`CostLayer` درست؛ سند موجودی اولیه (در صورت الزام حسابداری) طبق همان مسیر گام ۴.

### ۱۳-۵ — Rollback (M)
- `POST /admin/import/:batchId/revert`: معکوس‌کردن بر پایهٔ `before/after` همان ردیف‌ها، در یک تراکنش، idempotent.
- محصول ساخته‌شده → `softDelete` (نه حذف فیزیکی، چون ممکن است در سفارش ارجاع شده باشد).
- حرکت انبار → حرکت معکوس (`moveInTx` با نوع معکوس) نه دست‌کاری پروجکشن.
- `AuditLog` برای `import.revert`.
**پذیرش:** اعمال → revert → DB به وضعیت قبل برگشت (شاهد عددی count/قیمت/موجودی)؛ اجرای دوباره revert = بی‌اثر.

### ۱۳-۶ — API + قالب نمونه (S)
- روت‌ها زیر `admin/import`: `POST preview` · `POST :batchId/apply` · `POST :batchId/revert` · `GET :batchId` · `GET template` (قالب با نویسندهٔ CSV گام ۱۲).
- مجوز: `products.create` برای apply، `products.view` برای دیدن، مطابق الگوی RBAC موجود.

### ۱۳-۷ — UI ادمین (M)
صفحهٔ `/products/import`: انتخاب فایل → «پیش‌نمایش» → جدول تفاوت‌ها (با فیلتر `ERROR`/`UPDATE`) → «اعمال» → کارت نتیجه + «Rollback».
- لحن مطابق قاعدهٔ R1 پنل ادمین (ممیزی لحن گیت CI است).
- دانلود قالب نمونه + راهنمای کوتاه ستون‌ها.

### ۱۳-۸ — تست + شاهد (M)
`apps/api/test/phase18-bulk-import.spec.ts` با سرویس‌های **واقعی**:
۱. parse: نقل‌قول/کاما/BOM/رقم فارسی ۲. پیش‌نمایش: CREATE/UPDATE/SKIP/ERROR درست + DB بی‌تغییر ۳. اعمال: شمارش‌ها + قیمت/موجودی/CostLayer ۴. پیش‌نمایش کهنه → رد ۵. rollback پاک + idempotent ۶. گارد متن خراب (U+FFFD) رد ۷. مجوز کمتر از حد → ۴۰۳.
**شاهد runtime:** فایل ۱۰۰سطری واقعی روی API زنده + اسکرین‌شات پیش‌نمایش/نتیجه + شمارش DB قبل/بعد + Audit.

## ۶) ریسک‌های ثبت‌شده

1. **موجودی از مسیر غیررسمی نرود:** هر نوشتن مستقیم روی `stockQty`/`totalStock` دفتر و پروجکشن را واگرا می‌کند (سابقهٔ واقعی در همین پروژه). فقط `InventoryService.moveInTx`.
2. **متن خراب:** مسیر تازه = در تازه برای U+FFFD؛ گارد گام ۴ اجباری.
3. **تراکنش طولانی:** ۱۰۰ ردیف با چند سند/حرکت در یک تراکنش — سقف اندازهٔ فایل و تعداد ردیف باید صریح باشد (پیشنهاد: ۵٬۰۰۰ ردیف / ۵MB) و پیام روشن بالاتر از آن.
4. **قیمت‌ها:** سطح قیمت (`BASE`/`POS`/…) در فایل باید کد سطح باشد، نه نام کاربرپسند — وگرنه تطبیق مبهم می‌شود.
5. **تصادم با فرم ادمین:** ویرایش هم‌زمان یک محصول در فرم و پیش‌نمایش import → همان `previewHash` + بازبینی قبل/بعد جلوی بازنویسی کورکورانه را می‌گیرد.
