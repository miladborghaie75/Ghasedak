# برنامهٔ اجرایی تکمیل دستیارهای هوشمند قاصدک

> نسخهٔ ۲ · ۲۰۲۶-۱۰-۲۶  
> دامنه: دستیار خرید Storefront، دستیار فقط‌خواندنی Admin، و زیرساخت مشترک AI.  
> هدف هماهنگی: دقیقاً سه بخش کاری با مالکیت فایل‌های غیرهم‌پوشان؛ پس از تثبیت قراردادهای گیت صفر، سه بخش فنی موازی اجرا می‌شوند. ادغام و انتشار مرحله‌ای است.

## هدف و مرزهای قطعی

- مشتری فقط پاسخ فارسیِ مبتنی بر اطلاعات معتبر فروشگاه بگیرد؛ وقتی منبع کافی نیست، سیستم صریحاً ندانستن را اعلام کند.
- ادمین فقط تحلیل و خلاصهٔ داده‌های مجاز را بگیرد؛ هیچ عملیات نوشتن، ثبت سند، تغییر سفارش یا اقدام مالی از راه دستیار مجاز نیست.
- سهمیه/نرخ و حفاظت اطلاعات باید در محیط چندنمونه‌ای قابل اتکا باشد و شکست دفتر مصرف یا provider پاسخ جعلی نسازد.
- استعلام سفارش مشتری تا زمان اثبات احراز/تأیید هویت و تست جلوگیری از دسترسی متقاطع، خاموش بماند.
- کارهای داخل این برنامه با نوشته‌شدن برنامه یا گزارش‌های قبلی «انجام‌شده» محسوب نمی‌شوند؛ هر پذیرش نیاز به اجرای مجدد آزمون و شاهد تازه دارد.

## قواعد عدم تداخل و همکاری

1. یک هماهنگ‌کننده قراردادها را قبل از شروع ثبت و PRها را به سه مالک مجزا تخصیص دهد. تغییرات در branch/PR جداگانه باشند.
2. مالک هر بخش تنها فایل‌های فهرست‌شده در بخش خودش را ویرایش می‌کند. به فایل مالک دیگر نیاز شد، آن را تغییر ندهد: درخواست تغییر قراردادی/PR جدا بدهد یا هماهنگ‌کننده تغییر را به مالک همان فایل بسپارد.
3. API، Storefront و Admin ممکن است برای ادغام قرارداد مشترک داشته باشند، ولی مالکیت فایل مشترک ندارند. پیش از اجرای موازی، رابط بودجه و پاسخ خطا، روش عبور IP و مجوز API کتبی تثبیت شود.
4. هیچ کلید provider، cookie، شماره مشتری، transcript واقعی یا URL دارای credential وارد Git/log/fixture/prompt تست نشود. تست API فقط با `DATABASE_URL` صریح و DB ایزولهٔ غیرتولیدی اجرا شود.
5. هر PR شامل آزمون مرتبط، typecheck/build مربوط، `git diff --check`، توضیح ریسک و شاهد خروجی است. تغییر schema فقط در بخش اول و همراه migration و آزمون migration انجام شود. تست را skip یا assertion را ضعیف نکنید.

## سه بخش کاری غیرهم‌پوشان

### بخش ۱ — زیرساخت مشترک AI، سهمیه و اعتماد شبکه (P0)

**مالک:** مهندس API/زیرساخت. **فایل‌های انحصاری:**

- `apps/api/src/common/ai-budget.service.ts`
- `apps/api/src/common/rate-limit.middleware.ts`
- `packages/database/prisma/schema.prisma` و migration(های) مصرف/رزرو AI
- تست‌های زیرساخت مستقل: `apps/api/test/ai-budget*.spec.ts` یا فایل تست مالک این بخش
- فایل تنظیمات reverse proxy/edge فقط اگر در همین مخزن باشد؛ تغییر deployment بیرون مخزن نیازمند runbook/شاهد و مالک زیرساخت است.

**ممنوع برای این مالک:** تغییر `customer-chat.service.ts`، `admin-assistant.controller.ts`، هر فایل `apps/storefront/**` یا `apps/admin/**`. قرارداد مصرف بودجه با دو بخش دیگر را حفظ کند و تغییرش را پیش از ادغام هماهنگ کند.

**کارها:**

- [ ] مسیر شبکهٔ واقعی را ثبت کنید: reverse proxy/CDN، hop قابل اعتماد، و اینکه header ورودی در کدام نقطه حذف و بازنویسی می‌شود. اعتماد به اولین مقدار دلخواه `x-forwarded-for` ممنوع است.
- [ ] قرارداد کلید کاربر/نشست و IP مورد استفادهٔ rate limit را تعریف کنید؛ هیچ IP خامی در ledger ذخیره نشود. اگر توپولوژی تولید هنوز معلوم نیست، محدودیت مرزیِ شبکه را تا روشن‌شدن آن اجباری کنید.
- [ ] rate limit و سقف روزانهٔ کلاینت را از Map حافظه‌ای به ذخیره‌ساز مشترک/پایدار منتقل کنید؛ آزمون چند-instance، restart و header جعلی داشته باشید.
- [ ] سقف هزینه را میان `customer_chat` و `admin_assistant` مشترک و رزرو را اتمیک کنید: رزرو پیش از تماس پولی، تسویه با مصرف واقعی، و ثبت/برآورد هزینهٔ خطای provider. خطای DB یا رزرو قبل از provider باید fail-closed باشد.
- [ ] منبع نرخ، ارز، واحد تومان، حاشیهٔ محافظه‌کارانه، رفتار سقف و سازوکار آزادسازی رزرو ناموفق را در کد/پیکربندی واحد تعیین کنید؛ این اعداد از برآورد ثابتِ نامرتبط با provider production مشتق نشوند.
- [ ] خرابی ledger قابل مشاهده باشد؛ endpoint/لاگ نباید در خطای ثبت مصرف «مصرف صفر» یا موفقیت کاذب گزارش کند. داده‌های ثبت‌شده حداقل و بدون secret/PII باشند.
- [ ] migration روی DB آزمایشی خالی و rehearsal اجرا، و رویهٔ بازگشت/رفع migration ناموفق نوشته شود.

**پذیرش بخش ۱:** دو نمونهٔ API و restart یک quota مشترک ببینند؛ آزمون هم‌زمانی مجموع رزرو را بالاتر از سقف نبرد؛ DB/ledger ناموجود جلوی تماس provider را بگیرد؛ header جعل‌شده محدودیت را دور نزند؛ هزینه با سقف کل مقایسه شود نه به سقف جدا برای هر قابلیت؛ هیچ secret، محتوای پیام یا IP خام در ledger/log نباشد.

### بخش ۲ — دستیار مشتری و تجربهٔ امن Storefront (P0)

**وضعیت همین شروع:** logging شامل متن کامل پیام و متن خام خطای شبکه بود. در شروع اجرا حذف شد و آزمون‌های client مربوطه ۹/۹ pass و typecheck Storefront pass شدند؛ این فقط یک زیرکار است و پذیرش کامل بخش ۲ نیست.

**مالک:** مهندس Storefront/چت مشتری. **فایل‌های انحصاری:**

- `apps/storefront/lib/ai-client.ts` و تست آن
- `apps/storefront/components/commerce/ChatWidget.tsx` و تست‌های مرتبط
- `apps/storefront/app/api/ai/chat/route.ts` و تست آن
- `apps/api/src/customer-chat/**` و تست‌های customer-chat
- در صورت نیاز، محتوای منبع مشتری فقط با هماهنگی مالک CMS؛ از فایل‌های بخش ۱/۳ استفاده نشود.

**ممنوع برای این مالک:** تغییر فایل‌های زیرساخت بخش ۱ (`ai-budget.service.ts`, rate limit middleware، Prisma schema/migrations) و فایل‌های دستیار Admin در بخش ۳. فراخوانی بودجه از طریق قرارداد تثبیت‌شدهٔ بخش ۱ مجاز است.

**کارها:**

- [ ] محتوای چت، پاسخ، پیام خطای خام شبکه/provider و payload را از browser console حذف کنید. به UI فقط پیام/کد امن و قابل نمایش برسد.
- [ ] تاریخچهٔ محلی را اعتبارسنجی و محدود کنید؛ انقضای خودکار پیشنهادشده حداکثر ۷ روز، سقف تعداد/اندازه، پاک‌شدن کامل با دکمهٔ پاک‌کردن و رفتار امن برای storage خراب/غیرفعال را پیاده‌سازی کنید.
- [ ] Abort/timeout/قطع SSE/پاسخ ناقص را پوشش دهید تا loading گیر نکند و خطای خام/دادهٔ حساس نمایش داده نشود.
- [ ] منابع حقیقت را تعیین کنید: محصول/قیمت/موجودی از دادهٔ جاری و منتشرشده، سیاست ارسال/پرداخت/مرجوعی از محتوای تأییدشده و سایز از قواعد واقعی. پاسخ فاقد منبع به اعلام ندانستن و لینک صفحهٔ مرجع تبدیل شود.
- [ ] داده و نتیجهٔ بازیابی‌شده از کاتالوگ را به‌عنوان داده، نه دستور، به مدل بدهید؛ prompt injection نباید prompt داخلی یا اطلاعات غیرمرتبط را افشا کند.
- [ ] quick reply و ادعای «وضعیت سفارش من» را تا تکمیل احراز هویت امن حذف یا به مسیر پیگیری معتبر هدایت کنید. هیچ order code، تلفن یا شناسهٔ تأییدنشده‌ای برای برگرداندن سفارش کافی نیست.
- [ ] اگر در آینده lookup تصویب شد، فقط مالک سفارش تأییدشده و حداقل وضعیت لازم را برگردانید؛ آن توسعه ابتدا تصمیم معماری و آزمون مالکیت متقاطع می‌خواهد و خارج از شروع این بخش است.

**پذیرش بخش ۲:** تست fake-timer انقضا، clear history، JSON خراب/قدیمی، abort، timeout و SSE قطع‌شده؛ هیچ پیام/خطای شبکه در log نیست؛ محصولات unpublished/deleted یا قیمت نامعلوم به‌عنوان حقیقت عرضه نمی‌شوند؛ policy ادعایی لینک/منبع معتبر دارد؛ پاسخ خطای provider/DB ساختگی نیست؛ مسیر سفارش ناامن قابل استفاده نیست.

### بخش ۳ — دستیار ادمین فقط‌خواندنی و UI مصرف (P0)

**مالک:** مهندس Admin/API دامنهٔ مالی. **فایل‌های انحصاری:**

- `apps/api/src/admin/admin-assistant.controller.ts` و تست‌های آن
- `apps/admin/app/assistant/**` و تست‌های مرتبط
- فقط برای ثبت intent/date parsing اگر لازم باشد: فایل جدید مستقل در `apps/api/src/admin/` و تست هم‌مکان

**ممنوع برای این مالک:** تغییر سرویس بودجه/محدودکننده/DB بخش ۱، `customer-chat/**`، و `apps/storefront/**` بخش ۲. از API بودجه و مجوز تثبیت‌شده استفاده کند.

**کارها:**

- [ ] ماتریس intent بسازید: عبارت فارسی نمونه، گزارش مرجع، بازهٔ زمانی، دادهٔ مجاز به prompt، source link و fallback. intentهای موجود را با کد و سرویس‌های واقعی تأیید کنید؛ فهرست آغازین: سود/فروش، دریافتنی/پرداختنی، مغایرت بانک، چک، جریان نقدی، موجودی کم، سفارش باز، تسویه.
- [ ] فارسی واقعی شامل نیم‌فاصله، ارقام فارسی، مترادف، ابهام و چند intent را تست کنید؛ intent ناشناخته یا دوپهلو باید clarification بخواهد، نه گزارش اشتباه.
- [ ] امروز/این‌ماه/ماه‌قبل را براساس تقویم و منطقهٔ زمانی مصوب فروشگاه تعریف کنید و مرز ماه/سال و حالت تهی/منفی را بیازمایید.
- [ ] دادهٔ ورودی مدل allowlist و حداقلی بماند؛ نام/تلفن مشتری، شماره حساب، شماره/اطلاعات خام چک و فیلدهای surplus ممنوع باشند. فقط خلاصه و تحلیل، بدون ادعای اقدام یا نوشتن.
- [ ] دسترسی `accounting.reports` سمت API را برای signed-out، فاقد مجوز و دارای مجوز تست کنید. پنهان‌کردن UI جای گارد API را نمی‌گیرد.
- [ ] صفحهٔ Admin را به endpoint مصرف روزانه متصل کنید؛ سقف، رزرو/مصرف و قابلیت‌ها نمایش داده شود. حالت خطا/دادهٔ ناموجود با صفر اشتباه نشود؛ پاسخ همراه source و data-as-of باشد.

**پذیرش بخش ۳:** برای هر intent تست مثبت/منفی/ابهام و تطبیق عدد با گزارش اصلی؛ منبع و تاریخ درست؛ prompt فاقد دادهٔ ممنوع؛ endpoint فقط‌خواندنی و permission در API enforce؛ UI مصرف با endpoint/ledger هم‌خوان؛ نبود داده یا خطا به‌وضوح نمایش داده شود.

## ترتیب اجرا، موازی‌سازی و گیت‌ها

### گیت صفر — قرارداد و خط مبنا (مرحله‌ای؛ پیش از سه بخش)

- [ ] هماهنگ‌کننده سه مالک و بازبین، branch/PR جدا، و فایل‌های انحصاری را مشخص کند.
- [ ] یک صفحهٔ قرارداد تثبیت کند: API بودجه (`assert/reserve/settle` یا رابط معادل)، قالب خطاهای مشتری، IP/edge trust boundary، permission ادمین، منبع نگهداری history، منطقهٔ زمانی و منبع سیاست‌های فروشگاه.
- [ ] آزمون‌های هدفمند AI را روی checkout فعلی دوباره اجرا و خروجی تاریخ‌دار ذخیره کند؛ گزارش‌های قبلی فقط سرنخ‌اند و شاهد محسوب نمی‌شوند.
- [ ] مانع مستقل typecheck API در `apps/api/src/payroll/payroll.service.ts` را به مالک جدا بسپارد و تصمیم بگیرد که رفعش PR مستقل است یا مانع Go/No-Go. از اعلام «کل API سبز» تا تعیین تکلیف خودداری شود.

**خروجی گیت صفر:** مالکیت بدون هم‌پوشانی + قرارداد قابل مصرف هر سه بخش + baseline تازه. بدون این خروجی شروع موازی ممنوع است.

### موج ۱ — سه بخش موازی

پس از گیت صفر، بخش‌های ۱، ۲ و ۳ در branchهای جدا شروع شوند. قرارداد بخش ۱ باید پیش از تغییر مصرف‌کننده به بخش‌های ۲/۳ اعلام شود؛ اگر رابط تغییر می‌کند، هماهنگ‌کننده ابتدا قرارداد و سپس migration مصرف‌کننده را زمان‌بندی کند. مالک‌ها در فایل‌های خارج از بخش خود اصلاح مستقیم نزنند.

### گیت ۱ — بازبینی و ادغام مستقل

- [ ] هر PR فقط آزمون‌های پذیرش مالکیت خودش را اجرا کند و `git diff --check` سبز باشد.
- [ ] بازبین، secrets/PII/log، permission، migration و عدم تداخل فایل‌ها را بررسی کند.
- [ ] هر سه PR پس از بازبینی جداگانه ادغام شوند؛ آزمون‌های شکست‌خورده با skip، suppress یا تضعیف assertion پنهان نشوند.

### گیت ۲ — یکپارچه‌سازی روی API و DB غیرتولیدی (مرحله‌ای، بعد از گیت ۱)

- [ ] migration روی DB ایزولهٔ خالی و rehearsal اجرا شود.
- [ ] customer: محصول منتشر/ناموجود، پیام نامعتبر، quota، DB قطع، provider timeout/429/500، JSON و SSE و headerهای عبوری بررسی شود.
- [ ] quota/rate limit: چند instance، restart، درخواست هم‌زمان، header جعلی، DB/ledger قطع و جمع هزینهٔ دو قابلیت بررسی شود.
- [ ] admin: signed-out و بدون permission رد؛ مجوز درست پذیرفته؛ داده/source با گزارش SQL مرجع تطبیق شود.
- [ ] proxy فروشگاه هیچ cookie، کلید Admin یا credential provider را به endpoint مشتری forward نکند.

**پذیرش گیت ۲:** همهٔ آزمون‌های integration سبز؛ migration پایدار؛ quota مشترک و محدودیت شبکه پس از restart/بین instanceها برقرار؛ هیچ PII/secret در log/prompt/ledger ناخواسته نیست.

### گیت ۳ — Staging provider (مرحله‌ای)

- [ ] credential فقط از secret store محیط staging خوانده شود؛ مقدارش در shell history، فایل عمومی یا خروجی تست چاپ نشود.
- [ ] مدل، ارز/نرخ واقعی، timeout، پاسخ خالی، عدم پشتیبانی usage/SSE و خطای 429/5xx آزمایش شود.
- [ ] مجموعهٔ پرسش ثابت فارسی و prompt injection اجرا شود؛ پاسخ و اعداد با منبع مرجع مقایسه شوند.
- [ ] هزینهٔ واقعی تعداد محدودی درخواست با ledger مقایسه شود؛ تلورانس و بودجهٔ آزمایش پیشاپیش تعیین و راه توقف دستی حاضر باشد.

**پذیرش گیت ۳:** پاسخ مفید و منبع‌دار، اعداد بدون جعل، ledger در تلورانس مصوب، سقف جلوی درخواست بعدی را می‌گیرد و هیچ credential/اطلاعات مشتری نشت نکرده است.

### گیت ۴ — E2E مرورگر و دسترس‌پذیری (مرحله‌ای، بعد از گیت ۳)

- [ ] Storefront: چت، پیام فارسی، SSE chunk، لینک محصول، provider fail، قطع/لغو، history، انقضا و پاک‌کردن history؛ کیبورد و صفحه‌خوان.
- [ ] Admin: ورود/permission، پرسش پیشنهادی و دستی، loading، پاسخ، source، تاریخ داده، quota و حالت خطا.
- [ ] console/network پاک از خطای ناخواسته و متن حساس؛ transcript در URL یا credential در مسیر اشتباه دیده نشود.
- [ ] هرگونه order lookup در این مرحله خاموش می‌ماند مگر تصمیم جداگانه و تست دو مشتری با منع دسترسی متقاطع تأیید شده باشد.

**پذیرش گیت ۴:** همهٔ سناریوهای desktop/mobile و keyboard pass؛ loading گیر نمی‌کند؛ همهٔ خطاها پیام قابل‌فهم دارند.

### گیت ۵ — Go/No-Go انتشار

- [ ] API، Storefront و Admin typecheck/build، تست‌های مرتبط و suite API روی DB ایزوله سبز.
- [ ] خطای مستقل typecheck در Payroll رفع و دوباره بررسی یا با مالک، ریسک و پذیرش صریح release owner ثبت شود.
- [ ] migration/backup/rollback، secrets production، سقف آغازین هزینه و هشدار مصرف آماده باشند.
- [ ] پایش، مسئول incident، budget روزانه، kill switch، retention و رویهٔ خاموش‌کردن AI مشخص شوند.

**Go:** همهٔ P0 و پذیرش گیت‌های ۲ تا ۴ سبز، مانع Payroll تعیین تکلیف و runbook آماده است.
